# Run 39 失败协调节点用量修复

运行层原先只在 Agent 成功返回后将用量汇总到 `run_context.usage`。Run 39 的协调节点虽然在 `action_checkpoint.budget` 完整保存了 160 次模型响应，失败后却没有经过成功结算入口，页面因此只能读到上游的 38 次响应。

修复把入账移动到现有动作检查点保存事务：先保存真实预算累计值，再按同一节点的入账游标增加 Run 汇总，预算与汇总一起提交或回滚。游标仅记录已经汇总到哪个累计位置，额度仍由原来的共享预算控制。成功结算继续处理预留额度，并且不会再次累加已经入账的响应。

- 同一 Run 的节点重试保留累计游标，只增加新消费。
- 恢复到新 Run 时，继承检查点中的历史消费作为汇总基线；新 Run 只记录新增消费，共享额度仍保留全部历史消费。
- 自主阶段请求数在 SDK 准入时记录，申请整段预留不会先虚增一次请求。
- 未收到用量的请求仍占用原预算；汇总的 Token 字段只使用网关实际报告值，尝试次数字段包含已准入但中断的请求。

生产修改范围：`backend/modules/agent_platform/runtime.py`、`action_journal.py`，以及封装计量游标的 `usage.py`。未改序列化层，未修改线上历史运行，没有请求模型。

## 真实数据验收

命令：在 `backend` 运行 `.venv` Python 的 `scripts/qa/verify/verify_action_usage_real_data.py --output artifacts/verification/run39_failed_action_usage_real_data.json`。

1. 只读 Run 39，在 SQLite 副本中回放真实失败预算，得到 **198 次响应 / 198 次准入、输入 1,446,464、输出 164,814、总量 1,611,278**。把节点标为失败并重新加载 ORM 后，预算和 Run 汇总仍一致。
2. 只读成功 Run 36 的真实四次规划尝试（节点 943～946），依次回放失败、恢复、最终成功，累计 **61 次准入 / 58 次响应**，其中 3 次中断不伪装成成功响应。
3. 重复保存同一预算、重复成功结算和重复预留均不重复计费；累计用量倒退同时回滚检查点和 Run 汇总。
4. 从 Run 36 的节点 944 恢复到隔离新 Run，历史基线是 3 次准入 / 1 次响应；后续仅汇总 **58 次新增准入 / 57 次新增响应**。额度仍保留完整历史消费。
5. 已完成检查点复制到新 Run 后，新增用量和新增额度占用保持为零。

结构化报告：[run39_failed_action_usage_real_data.json](../../backend/artifacts/verification/run39_failed_action_usage_real_data.json)。编译与修改文件空白检查通过。

这些检查验证真实历史消费在生产持久化函数中的回放，不等于一次新模型运行或 MySQL 并发锁验收。旧的 `verify_action_quota_real_data.py --run-id 31` 因 Run 31 已缺旧版逐节点复审图而停止；该旧脚本不计作本次通过证据。线上 Run 39 的历史汇总保持原样，下一轮正式运行才直接使用新路径。
