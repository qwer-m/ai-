# Run53 人工确认后的失效范围与支持复核容量

仅使用已保存的 `final-snapshot.json` 本地分析。脚本 `audit_policy_invalidation_local.py` 只加载仓库明确列出的纯函数 AST，不导入数据库模块，不读写数据库、不发模型请求、不修改源码或服务。数值证据见 `policy-invalidation-capacity-audit.json`。

Approval13 已获用户真实答案，两项重叠确认共同涉及三个 fact_id：P0005-5、P0005-7、P0014-S0-E442-f6，答案均为“采用10月29日反馈：全部开放，绿点标记完成状态”。

| --- | --- |

| action26 rebuild_business_plan | 28个草案结果、1个全局规划结果 |

支持输入按当前冻结参数本地重建共41个请求；已有14个专业回执的完整 input_hash 全部在重建请求中找到。剩余27个业务请求尚未形成已验收专业结果。本报告未把专业回执数量直接当作模型 HTTP 请求数。

## 全部重算的代码原因

1. `conflict_confirmation.apply_conflict_decision` 第66行保存真实答案后调用 `clear_source_authority`，并清除下游候选缓存。
2. `test_generation_planning_agent.clear_source_authority` 第1127行把当前已验收治理结果置为 None，并直接把整个 `PlanningDependencies` 仓替换为空，全部旧归属与支持依赖因此不可再采用。
3. `test_generation_agent.apply_authority_action` 第724行重新从提取时的 `planning.source_semantics.authoritative_facts` 合并本次稀疏治理补丁，没有以上次已验收治理结论为修订基线。
4. 本轮治理结果相较答复前改变28条事实的治理字段，有效事实274→297。25条变化事实的最终值逐字段等于最初提取的 raw fact：旧失效、未决、参考判断没有在新补丁中重报，就退回 raw 默认值。三个答案直接关联的事实中仅两个发生治理变化；其余26条变化不能仅凭这次确认视为必须变化，也不能未经语义核对就宣布全是错误。
5. 变化后的有效事实重分批，26批→28批。`_retained_records` 第157行使用完整输入 hash；`planning_batch.batch_count`、`batch_number` 进入输入。当前有7批的业务内容完全等于旧批，但展示批号或总数不同，完整输入匹配为0，因此28批均未保留旧草案。
6. `coverage_group_origins`、`ownership_inputs`、`support_input` 把全部 `policy` 写入每项身份；SDK `invoke_agent` 第2241行又将全部 `_user_confirmations` 注入所有专业调用的原始请求。即使业务来源未变化，口径存在与否也使每项专业请求身份变化。

这里存在三个不同因素：治理基线被丢弃造成范围漂移，批次展示元数据造成假失效，以及全局口径参与全部身份造成扩大失效。不能统一解释成“用户答复是全局 policy，所以全部重做是必要的”。

## 哪些确实应重验

人工答案所涉及的真实事实、其明确 `governed_by` 来源关系闭包、据此形成的草案覆盖和支持关系必须重验。若重规划确实改变业务边界全集，现有归属模型依赖全部业务边界目录，全部归属重新判定有合理性；不能在目录改变后仅因某个 scope 原文未变就机械保留旧归属。

若某范围的完整事实闭包、业务边界和适用答案均未变化，其旧结果没有因为一次局部答复就必然失效的依据。全局协调者和全局规划需要知道全部答案；每个叶子草案和单意图支持请求不应仅为保持“全局”二字而复制无关答案、丢弃旧治理结论。当前仅1个新草案批次直接包含答案事实；这只是直接 ID 关系，不是对全部业务语义影响范围的最终裁决。

## 模型输入的重复量

`_support_review_inputs` 第1049行已做到每个请求内每 scope 原文只放一次；没有发现同一请求内把完整 scope 原文简单重复逐事实附加的错误。输出容量分批会让同一候选事实和原文跨请求重复发送：本轮9个模块产生41个请求，14份唯一 scope 文本累计额外发送290次。

主要的可无损去重对象是 `candidate_facts.source_context`：41个请求累计1435份上下文，按每请求完整相同值计仅251份不同上下文。候选事实部分累计3,023,855 UTF-8字节，scope原文部分565,826字节。原文与上下文还存在少量文本重叠，但它们承担不同语境责任，不能仅凭内容相似删除其中一种。

直接复用现有 `authority_source_review_view` 的共享来源编码，只处理候选事实的原始元数据，并保存同请求的 `source_records` 目录，得到：

| 本轮41个业务 payload累计 | 当前表示 | 无损共享后 | 减少 |
| --- | ---: | ---: | ---: |
| JSON字符 | 2,189,835 | 1,454,695 | 33.6% |
| UTF-8字节 | 3,633,779 | 2,147,387 | 40.9% |
| 原容量分批估算 token | 1,810,976 | 969,846 | 46.4% |

全部候选事实按原字段、原值完整还原相等，没有删业务条件、事实、原文或引用。剩余27个业务 payload累计UTF-8字节2,130,729→1,341,428。单次业务 payload最大UTF-8字节134,788→76,892。仍为41次支持请求；本方案不宣称改变输出容量导致的分批次数。

这些只是专业模型业务 payload体积，不是实际账单 token，也不是 SDK完整请求准入值。当前支持模型投影不包含 `_user_confirmations`/`user_decision_context` 字段，真实口径仍通过 SDK 生成的指令进入模型；完整指令、工具和 schema 必须一并计费准入，不能拿本报告大小直接覆盖已用预算。

## 最小修复建议

1. **沿既有治理链保留基线。** 人工答复作为已批准事实范围及来源关系的增量修订，给同一个治理能力完整来源上下文和上轮已验收治理基线；限定应修订的真实引用闭包，边界外治理字段保持。对超出闭包的变更要求明确来源依赖，再进入既有验收；不要因输出稀疏就默认抹去旧结论。未变依赖继续由原 `PlanningDependencies` 保存与复验。
2. **消除展示身份。** 从草案专业业务输入中移除 `planning_batch` 的批号、总数等位置字段，显示和调度继续使用现有 `business_planning_batch_plan` 统计产物。保留全部事实、case_budget和真实作用域；输入身份直接由完整业务内容决定，不另加忽略字段的缓存特判。
3. **同一适用范围同时作用于模型与身份。** 全局协调保留全部人工口径；专业子调用按明确事实/来源闭包选择相关口径。必须同时用于输入、指令、验证和依赖身份，不能仅从 hash 去掉全局口径却继续把全部答案送给模型，否则会错误复用。业务边界全集真实变化时仍使相应全局归属失效。
4. **复用来源共享编码。** 在现有支持模型输入投影中使用无损共享的 `candidate_facts` 和 `source_records`，专家说明按 `$ref` 读取完整原始上下文；现有完整事实/原文留作可信验收。专业输出契约无需扩大。预算仍测量最终实际发送的完整请求，不调大 cap，不截断内容，不增加本文档专属规则。

这些是下一版本的源头修复建议，未应用到冻结 Run53，不重写其历史 input_hash、治理结果、预算或回执。增额续跑是否实施由根代理沿正式平台入口另行处理，本报告不代替其授权或成功证据。
