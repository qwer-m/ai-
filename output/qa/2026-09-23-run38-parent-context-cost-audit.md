## 当前观察与范围读取里的具体内容

初审后当前观察的 117,219 字节中，`problems` 为 71,984，`planning` 为 21,786，`review` 为 10,047，`generation` 为 9,995。47 条问题的 `reported_problem` 原文合计 47,597 字节，其他字段包含问题 ID、事实 ID、相关批次和来源版本。当前问题是父决策的真实依据，不宜作为过期历史直接删掉。

各阶段 `planning` 内容哈希一致，为现有规划目录而非重复追加的历史。主要组成是 `planning_batches` 11,323 字节、`route_gaps` 7,687、`source_items` 1,003。它每轮仍有成本，但压缩它需要另行定义当前决策必需目录；本次版本化历史读取不必改变这条数据流。

第二次检查中，顶层原生成输入为 27,225 字节，与第一次检查中的输入完全相同；`review_scopes` 为 49,664。该审查范围的输入占 41,306，含测试用例 13,587、设计项 10,658、审查事实 10,038、绑定 6,221；另有旧审查结果 8,294 字节。这是完整取证结果，读取当时合理，后续状态变更后不应永久视作当前。

## 已证实的过期候选

事件 61 检查 item8，得到生成批次 `M003-B003` 和审查批次 `R-004`，范围为 `TC-017..TC-026`。事件 72 完成 R-004 修复后，10 条候选中的 **8 条正文哈希已经变化**，而原读取结果及旧 8 条审查意见仍留在 SDK 历史中。这里只证明内容发生变化，不宣称新候选语义已通过。

因此，根线程拟采用的版本化读取方案有直接数据依据：保留最近且当前版本有效的完整结果；当完整领域状态改变后，仅在模型视图把旧结果换成携带原参数、结果哈希、状态版本和过期说明的小回执。不要用旧 item index 自动重读，规划或布局变更可能改变索引对应范围。

按完整 `action_state` 判断失效会让无关批次修复也使旧检查过期。这是保守失效，代价是父可能重新读取；不会把旧内容冒充当前。共享预算位于 checkpoint 的单独字段，不在 `action_state` 内，因此单纯请求计费不会使读取过期。

## 现有代码入口与边界

- `sdk_adapter._function_tool`：handler 和输出 Schema 成功后才调用 `record_result`；可在现有位置传原始参数，拒绝反馈不得登记成成功读取。
- `sdk_adapter._PersistentStateInputFilter.record_result / __call__`：扩展明确配置的快照工具记录，继续核对完整结果哈希，仅改模型视图；调用/输出配对、顺序、当前观察、原 journal 与日志不变。
- `semantic_identity.agent_contract`：现有执行语义包含除 `result_cache` 外的完整 `runtime_config`，新增声明会自然进入冻结身份。
- 新会话没有可信标记的历史内容应继续保留；不能靠字段形状猜测任意取证结果可删除。同版本同工具同参数去重时，必须在本次输入内至少留下最近一份完整结果。

终态还剩 221,481 输入额度，下一请求保守预留需 245,787，因此发生准入硬停。历史快照内容总量足以显著影响这一边界，但本只读审计不等同于过滤器验证或模型重跑，不能保证收敛后完整任务必然成功。
