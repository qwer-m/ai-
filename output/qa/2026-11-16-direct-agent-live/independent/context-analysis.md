# Run64 只读上下文审计

结论：本轮没有调用图片、RAG或独立评审。8次模型请求均为主Agent，197,116已报告token中192,187为输入（97.50%）。失败发生在第9请求发送前的保守准入，不能说实际已经消耗305,315。

## 可证实的重复

原始SDK请求正文未持久化，因此不伪造完整请求，也不把下面字节分项直接归为供应商token。实际诊断记录8请求SDK上下文JSON累计657,594B。实际不可变回执可以精确取出工具返回内容、失败计划参数以及各状态原文。

- 首次read_source返回32,621B，其中正文24,533B，evidence_catalog7,750B；恢复后返回33,298B，其中正文25,012B，catalog7,948B。
- `_PersistentStateInputFilter.__call__`保留完整初始观察user消息，每请求又在尾部追加完整当前观察；read_source结果再次携带相同catalog。按真实回合位置计算，catalog原始JSON值片段共171,490B（不含外层字段与SDK再次转义）。
- 两次失败计划参数分别5,130/5,082B。`_compact_committed_actions`只压缩completed写动作，所以即便seq4已成功，失败seq2/seq3的完整参数仍分别留在随后4/3回合中，共35,766B。
- 原始来源正文在有效read_source快照中保留，属于必要业务证据，不能简单删除。其重复JSON片段为147,677B；这是共享上下文总体成本，不能全称为浪费。
- 每条catalog里的64字节content_hash在仅模型展示层重复；去掉该展示字段（完整hash留state/验收）可使初始catalog7,750→4,634B，恢复catalog7,948→4,750B。按上述回合位置是68,962B原始JSON片段，实际计费收益未测。
- 初始人工确认system补充说明4,565B，恢复后6,845B，来源AP原文与同范围问题必须保留，但可去掉与当前领域输入重复的技术上下文。

## 建议沿现有组件修复

1. 主会话初始输入只固定不变任务规格/来源身份；当前状态只由每轮尾部观察提供一份，不把首次完整状态永久留在前缀。继续核对初始输入身份，不取消Journal/CAS校验。
2. `read_source`返回所读正文、证据ID/页码和读游标即可；目录由唯一当前观察持有，避免工具结果再次附整目录。若需要目录定位可按真实state版本标记，不放松引用验收。
3. 对同一expected_version的失败写候选，只有后续同域版本已经成功提交后，才在模型视图改为参数hash/错误摘要/替代成功调用ID；尚未解决的最新失败仍保留完整参数。永久Journal不改。
4. 减少模型目录中的技术字段（逐条hash、重复页面参数），完整来源、指纹、区域仍在state和工具结果，按需要读取。不要把词、条件或引用正文压成缺失语义的关键词。
5. 当前tail先`_runner_input`把observer转成JSON字符串，再把该字符串放进`current_state`整体json.dumps，造成额外转义。文本持久主会话可在一处构造结构化current_state再序列化，retry反馈单独明示；不改变原始状态或费用账本。
6. 费用准入继续区分reported与pending保守预留。实际total197,116，下一请求投影305,315意味着本次未通过预算门禁，不等于供应商已收取305,315；不能任意降低估计系数来掩盖上下文问题。

另外两个已向root报告的业务接口问题：COV编号正则仅在Python隐藏校验中、公开Schema缺少pattern；coverage items被模型当局部修订提交，但工具整份替换导致19→1。root已并行修复，子代理未改生产文件。
