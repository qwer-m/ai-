审计日期：2026-09-28。对象：CRM 项目 9、Run 39、文档 280、第 11 页的真实来源候选，以及模块 2 的三个真实覆盖意图。本次没有调用模型、改生产代码或写数据库。

## 结论

三项问题所需的原文均已进入模型的实际请求。当前 `source_context` 没有错行，也没有遗漏升级列标题；双向核对实验已经在启动期正确识别列标题的“连续 2 个月”。因此不能把余下漏判归为来源仍未流通，也不能据上下文有重复就认定长度是失败原因。

独立存在的改进点是：当前来源锚点只有行级 `block_id`，没有表达“这个事实对应这一行哪一个单元格”。同一行的进入、维持、升级、降级事实带着相同的整行上下文。这个关联缺口会增加阅读负担，但本轮证据不足以证明它是两项剩余漏判的唯一或主要原因。

按当前排期，先验证现有真实输入在推理模式及兼容工具选择配置下的表现；本审计不扩展生产锚点契约，不按 assertion 猜列，也不改写旧模型断言。

## 当前上下文组织

模型输入有 29 条真实候选事实，其中 20 条带表格上下文。每条表格事实保留首行和自身所在行；本次每行 5 列，因此每条包含 10 个 cell 实例。

- 总计 200 个 cell 实例，按 `(table_id,row_index,column_index,text)` 去重后为 30 个真实 cell。
- 单元格正文累计 1,892 字符，去重后为 361 字符。该统计仅针对 cell.text，不是 HTTP 请求大小或全部 prompt 字符数。
- 升级列标题重复出现 20 次；每个业务行对应的四条事实重复相同上下文。
- 各事实只含 row 0 和自己的业务行，没有把其他业务行误接到该事实。
- 三项关键事实的上下文都包含完整表头及完整相关单元格，因此属于“已到达但未充分使用”，不是“表头丢失”。

`source_context` 按行列坐标能读懂，但表头与正文分置两行，加上多列、多事实重复，要求模型自行定位并组合对应列。现有 reason 是自由文本，结构契约没有要求逐条交付“引用了哪些真实条件及其与意图的对应关系”；因此模型可以在某一项核对表头、另一项只匹配 assertion，同时仍通过格式和引用完整性检查。

## 行级锚点与字段粒度的区别

1. `test_generation_schemas.py` 的 `SOURCE_SEMANTICS_AGENT_ANCHOR_SCHEMA`（约 1742 行）只允许文档 `document_id/page_number/block_id`；来源 prompt 也禁止 quote、source_span 和 block_id 数组。模型不能提交更精确的单元格引用。
2. `test_generation_semantics.py::_validated_document_anchor`（约 1757–1783 行）在模型仅给 block_id 时从真实块派生 quote/source_span。这一行为保证引用真实，却不能把横跨多列的原文本块缩成某一列。
3. 真实 `P0011-T0012`、`P0011-T0018`、`P0011-T0021` 分别横跨启动期、成熟期、扩店期所在行的五列。一个 block_id 在五列 segments 中出现，不是某一个 cell 的唯一标识。
4. `_source_context_for_anchor`（约 2155 行）使用 `_project_table_contexts`（约 167 行）按命中的 block_id 选择整行和首行，再从真实 segments 拼成 cell.text。行选择正确，但输出未表达该事实具体引用哪些列。
5. 真实 source inputs 的 `cell.segments` 已保留 `block_id/text/original_source_span`；这些是后续增强关联时可直接复用的数据，无需新造事实或添加新的 AI 审核层。

由此只能证明当前是“事实 → 原文本块 → 原表行”的关系。不能把当前代码解释成已经有“事实 → 精确单元格 → 对应表头条件”的关系，也不能根据断言中的业务词在后处理里补猜此关系。

## 最小后续方案与边界

当前不实施新增锚点字段。先完成相同真实输入的推理配置诊断，按三项具体语义问题验收，不能只计 supported/unsupported 数量。该诊断能回答模型是否可在已有完整原文上完成正确判断。

若后续仍需增强来源定位，优先在已有来源 anchor 契约中增加真实单元格选择，而不是新增审核 agent：让当前来源 agent 选择已提供网格的 `table_id/row_index/column_index`；平台验证 cell 确实存在、与当前允许 block/提取范围有交集，原文和坐标仍从真实 segments 派生。非表格事实不引入该字段。当前仅行级锚点的历史输出不能被 assertion 词匹配自动补成精确列引用，应重新提取或明确保留原有粒度。

精确关联成立后，再从已有事实投影统一呈现“真实目标 cell + 同列首行原文 + 必要行上下文”，避免把同行其他行为混入本事实，也不让代码替模型决定哪段业务文字优先。保留 canonical 可追溯数据，模型显示可集中呈现重复表格；这只是可读性优化，不应声称它等价于语义正确。

如果需要可验收的逐项核对，可以在现有支持审查回执内表达每个已引用规则的原文 cell 引用与覆盖意图片段，并校验引用存在、片段逐字真实、应审项完整。它仍由现有 reviewer 完成；确定性代码不读取 reason 关键词裁定业务冲突，也不能把结构证据齐全误当成语义无误。是否有必要扩展此回执，应由下一次真实诊断决定，本轮不实施。
