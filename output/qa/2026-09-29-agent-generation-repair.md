# Agent 生成耗时与失败修复

## 诊断依据

- 原始截图对应 Run 43，来源为真实文档 280，目标 50 条用例。总耗时 1,268 秒（21 分 08 秒），自主生成节点耗时 892 秒。
- 原来源路由串行执行 24 次模型请求，行动耗时 463 秒。支持审查在第八个模块中连续提交错误结构，最终触发 SDK 的 `MaxTurnsExceeded(6)`，整个协调阶段因此失败。
- 真实错误回执包含额外 `arguments` 包装、非法 JSON。不是主阶段 160 次请求预算耗尽；原节点仅使用了 43 次请求。

## 修改

1. 完整对象的提交 Schema 在 SDK 严格化不会改变原契约时启用 strict；具有可选补丁字段的 Schema 保持原语义。错误字段定位直接来自实际提交对象，不拆包装、不放行坏候选。
2. 独立路由和支持审查复用原专家调用入口，使用运行配置中的并发数 6；共享原预算和持久回执。平台异常会取消并等待其他任务结束；局部会话额度耗尽返回协调 Agent，成功回执保留。
3. 原生 SDK 六轮上限统一归入局部会话额度错误。专家仍保持六次局部上限，协调阶段总预算不重置。
4. 请求时序保存到成功/失败诊断中；反馈给模型时去除整阶段请求时序，保留候选校验错误、字段位置和预算状态。
5. Run 44 另外暴露视觉提取在 5,000 输出 token 处截断。文本和视觉使用相同事实输出契约，现共用原文本提取的 15,000 token 容量配置。未按文件名、页码或文档类型添加业务特例。
6. Run 46 暴露 SDK 动态隐藏工具导致的阶段恢复缺陷。已授权工具现保持稳定注册，当前合法行动仍由既有领域守卫逐次校验；过期调用返回原有 `OutputValidationError` 反馈。删除原动态可见性缓存及反复计算状态指纹的逻辑，未新增允许过期行动执行的分支。
7. Run 47 暴露视觉页输入预算把页面图像 Base64 字节直接计入输入 token。预算现在只按真实 `input_image` 数量使用视觉协议预留，完整上下文字节仍单独保留为诊断数据。Run 47 的真实复查请求因此从约 104 万预留降至 15.9 万，模型实际消耗 23,383 输入 token，准入不再被 Base64 放大误拒。
8. Run 47 的真实复查还暴露来源 Agent 偶发改写 `document_id/page_number`。没有放宽锚点校验；通用视觉来源指令已明确身份字段必须从当前输入原样复制，校验反馈会返回期望值和实际值，便于模型在剩余轮次修正。

## 已取得的真实验证

- 原 Run 43 失败专家输入单独调用真实模型：34.415 秒、2 次请求，通过完整契约。当前模型服务仍可能返回无效参数，strict 不是服务端强制遵循的证明。
- Run 45 来源分析全部通过。第 6 页首次尝试成功，实际输出 4,458 token；这一结果不能单独证明旧容量必然失败，旧容量截断的直接证据来自 Run 44 后两次均输出 5,000 token 的坏 JSON。
- Run 45 路由 25 项全部完成，用时 219 秒（3 分 39 秒）；原 Run 43 为 24 项、463 秒。请求时间记录证明峰值并发为 6。任务内容由模型生成，故该比较是实测运行对比，不是控制变量性能基准。
- Run 45 初轮 11 个支持审查全部提交通过。追加核对期间真实触发一次局部六次耗尽，协调 Agent 保持运行，改选核对输入后继续取得验收结果。不能据此声称原失败输入在同一运行中原样重试成功。
- 对 Run 45 原始错误回执执行真实数据回放：模型反馈从 62,149 字符降至 8,444 字符；6 次候选拒绝信息保持一致，51 条请求记录未从原诊断中删除。
- 两项内置工作流/定义检查通过；修改模块编译和 diff 空白检查通过。没有使用 mock 模型或 mock 业务数据。
- 常驻 Celery worker 空闲检查通过后平滑重启，新 PID 26972；HTTP 健康检查返回 MySQL、Redis 正常。这不等于完整 HTTP/Celery 生成链路已经验收。
- Run 46 最新失败状态与真实历史调用参数回放通过：工具在 SDK 中仍注册，领域守卫拒绝过期调用并返回当前合法行动，业务状态和原数据库均未变化；没有调用模型。
- 旧 `verify_generation_action_availability_real_data.py` 的断言已调整为稳定注册和领域拒绝，但其默认 Run 38 历史状态版本已不受当前规划运行时支持，执行停止于状态版本校验，不能计为通过。没有改写历史快照绕过校验。
- Run 47 的真实图片预算回归实际调用成功并保持数据库、运行状态不变；来源候选因模型提交了错误页/文档锚点被确定性拒绝，说明预算修复成立但语义结果仍需模型修正。
- Run 48 使用上述身份反馈修复版本正式执行：来源文本、来源视觉、规划批次均通过，随后 4 次协调节点尝试遇到 3 次真实模型连接异常；恢复后继续使用已保存的专家回执，最终在输入预算准入处安全停止（已占用输入 1,992,954，下一次预留会达到 2,042,595，超过 2,000,000 上限），没有超额发起模型请求，也没有交付用例。

## 完整验收状态

Run 46 最终失败，耗时 1,740 秒（29 分钟），交付 0 条。它经历模型连接超时并从回执恢复；局部六次耗尽已转为可纠正反馈。最终在修订草案、重建业务计划后，模型调用已被 SDK 隐藏的 `review_planning_route_gaps`，以 `ModelBehaviorError: Tool ... not found` 结束。该问题已按第 6 项修复。

Run 47 最终失败，耗时 1,860 秒，交付 0 条；稳定工具注册没有再次触发 `Tool ... not found`，但视觉页复查被来源锚点校验拒绝。

Run 48 使用当前视觉预算和锚点反馈修复版本，耗时 1,728 秒，交付 0 条。它不是业务候选失败，而是 3 次 API 连接异常后的恢复重试把保守的未知请求预留消耗到输入预算边界；预算守卫按设计拒绝第 121 次预留，避免超额调用。

Run 45 为诊断模型反馈体积问题而主动取消，不是完整成功。取消入口触发项目默认只保留一次历史的清理策略，数据库 Run 43、44 已被清理；原始来源、检查点和诊断快照保存在下列本地证据中。没有手工重建历史数据库记录。
