## 本轮实际变化

原图中从 `resolve_planning` 到 `resolve_final_review` 的 11 个中间节点由一个持久 `resolve_generation` 接管，全图从 24 节点变为 14 节点。保留 7 个来源与初始草案节点，以及 6 个验收、执行链和交付节点。外层依赖和最终落库仍由代码控制，中间行动由同一协调 Agent 根据当前状态选择。

协调者可以接受规划、协调权威事实、生成某批、独立审查、局部修复；发现上游问题后，也可以返回草案或业务规划，调整事实分组与批次预算，再生成并复审。复用原有专业 Agent、准备函数、后处理和领域状态，删除被替代的两套公开协调 Agent 及中间阶段工具。

生成专家新增 `report_generation_scope_problem` 出口，报告真实事实、设计关联、原文条件和具体矛盾。它是 `planning_feedback` 类型的待判断主张，不是已生成用例，也不是自动批准的重规划指令。仅父协调者明确授予的备用契约可以接收报告；普通用例仍按原完整契约验收。

## 数据和状态边界

- 来源身份与用户总用例预算不变。开始生成后保留原事实目录；不能增加总预算来消除数量拒绝。
- 权威、生成和独立审查按完整准备输入决定复用。完整输入包含事实、设计关联、批次身份和数量；仅 fact_id 相同不能证明语义未变。
- 调整模块后仍要求每条有效事实恰好进入一个分组，设计覆盖完整，所有批次预算总和等于用户输入。
- 旧行动、旧审查输入和旧批准不能写入新版本。再次回到完全相同的审查输入时保留原全局审查历史，不能通过重建状态反复抽取批准。
- 父协调者、托管专家和场景咨询共享总预算；生成专家及其咨询同时受原 6 次局部上限约束。新的默认总请求上限为 160，Token 硬上限仍为 2m/800k/2.8m；显式更低配置和旧 Run 限额不变。
- 执行和语义指纹使用同一份冻结定义，覆盖协调者、托管生成专家及其场景专家。禁止继续嵌套托管协调层和更深的咨询层。

## 验证中发现并修复的接入问题

统一阶段暴露出原 SDK 只允许一层专家身份的问题，以及合法范围报告在 Runner 返回后又被普通用例 Schema 拒绝的问题，两者已在现有链路中修正。

全局审查按契约只看到用例索引，不返回事实编号。问题定位现沿当前 `case_id → case_fact_bindings → 生成批次 → 规划批次` 的既有数据流补齐，原审查差异保持原样；没有把定位信息伪称为评审模型引用的原文。现有真实全局审查记录没有差异，尚未覆盖这一分支的自然触发。

多批次行动原先要等待所有专家调用完成才保存状态，相比旧 `agent_map` 存在单项成功结果丢失风险：后续项发生 504 时，之前成功项需要重做。已复用现有行动检查点保留逐项已验收结果，同时保持父领域行动原子提交和已消耗预算。

[专业回执真实回放](../../backend/artifacts/verification/run36_managed_receipts_real_data.json)组合 Run 36 的真实成功候选与既有 504 回执，在隔离 SQLite 父行动失败、关闭重开后，经实际 SDK 托管入口复验并复用成功项；模型请求为 0，预算不重复计费。完整输入、guidance 或执行契约变化不能命中旧回执，当前候选验收回调仍会执行。此验证不是新发生的在线 504，也不覆盖进程强杀；模型返回至回执落盘之间仍有单请求重做窗口。
