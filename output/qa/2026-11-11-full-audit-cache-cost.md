# 缓存、请求构造、Token 计量与成本护栏审计

审计时间：2026-11-11。范围：当前工作区代码、已安装 SDK 源码、现存 Run 43–47 真实监控与 Run 45/46 原始节点快照。本次没有发起模型请求、查询余额、创建或重跑任务，也没有修改生产代码。仅生成本报告及汇总 JSON。

## 已核实的事实

五轮报告均为 `failed`，应用节点缓存事件 `node_cache_hit` 合计 0。账本已报告模型请求 622 次、输入 4,783,603 tokens、输出 1,376,471 tokens、总计 6,160,074 tokens；包括未知结果预留的 attempted_requests 为 636。此范围不包含 Run 42、独立探测和更早历史，不能作为完整账单，也不能用 attempted 数直接认定厂商成功计费次数。

可重算数据：`output/qa/2026-11-11-full-audit-cache-cost-evidence.json`，来源是五份现有终态 monitor JSON。不得把各 attempt 的累计 checkpoint 相加，避免重复计量同一共享账本。

厂商的前缀缓存和应用的结果缓存是两种机制。上述 0 是**应用节点结果缓存**；项目丢弃了厂商缓存用量详情，因此现有日志不足以核实“厂商每次均未命中”，也不足以还原准确金额。用户的厂商后台账单可以作为另一项事实，但本审计没有访问该后台。

## C1 · P0 · 只有每个实例的技术额度，没有支付层的累计止损

**证据**：`backend/core/settings/config.py:80-91` 明确规定按 Agent 实例计算，默认 160 请求、200 万输入、80 万输出 tokens；`backend/modules/agent_platform/service.py:59-76` 也按实例归一化。`service.py:93-105` 每个新 Run 产生新的 logical_task_id 与空的实例用量账本。`autonomous_budget.py:220-245` 拒绝的是当前共享父/子 Agent 会话的 token/request 额度，而不是用户、项目或同一需求跨 Run 的累计金额。上游 source_text、source_vision、plan_batches 映射实例仍各自申请额度。

**实际触发**：Run 45 的 resolve_generation 使用完 160 次；整轮仍记录 181 次（另外 21 次是上游）。接着新建 Run 会再次获得新额度；同一需求反复修改并重建 Run 时没有累计支付上限。各轮局部不超限，账户仍可以被耗尽。

**修复设计**：增加用户/项目/逻辑任务三个层次的独立支出账本，所有业务、重试和探测入口在实际发 HTTP 前原子预留；按模型及命中/未命中/输出价格快照计算货币预留，收到真实 usage 后结算，未知用量独立标记待核账。单次执行额度继续保留，但不能替代跨轮总预算。同一需求的修复尝试应沿用逻辑任务身份并累计费用。技术改动验收先只用现有真实记录离线回放；未设置明确小额验收预算前不能再靠完整实跑迭代。

## C2 · P0 · 厂商缓存、推理用量被丢弃，缓存和金额无法核账

**证据**：`backend/modules/agent_platform/request_diagnostics.py:173-181` 每次响应仅保留 requests/input/output/total 四项。`sdk_adapter.py:2420-2428` 最终结果再次仅提取四项；`autonomous_budget.py:164-185,256-269` 的 reported_usage 同样只有四项。项目搜索未发现 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`cached_tokens` 或 `reasoning_tokens` 的计费归一化实现。

安装 SDK 的 `agents/models/openai_chatcompletions.py:253-261` 仅将标准 `prompt_tokens_details` 和 `completion_tokens_details` 映射到 Usage；即使这些详情存在，当前应用仍会丢弃。若供应商返回原生 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 而不填标准详情，此处也没有将其归一化的适配层。

**后果**：不能区分真实未命中、SDK 未映射、应用未保存三类情况；总输入 token 不能直接乘统一单价得到账单；推理输出占比也不可见。连接池复用不会等同于模型前缀缓存命中。

**修复设计**：在真实 HTTP 响应适配边界统一保留 provider 原始 usage 的允许字段与规范 usage，至少区分 cached_input/uncached_input/output/reasoning、是否报告、request_id、response_id、模型路由、价格版本和币种。字段未报告必须存 unknown，不能伪装成 0。每次请求的账本独立持久保存，诊断截断不能截断计费事实。先用现存原始真实 usage 验证解析；若原始响应已经丢失，应明确历史不可补算，不能编造缓存数。

## C3 · P1 · 应用结果缓存绑定整轮成功，失败轮次中已完成的纯节点全部重算

**证据**：`backend/modules/agent_platform/run_repository.py:505,511-520` 只允许父 `AgentRun.status == success` 的成功节点进入候选。`result_cache.py:105-119` 才检查输入与语义哈希，`128-149` 已有只读的完整原始输出复验。因此失败轮次里 source_text/vision/plan_batches 即使各自 success，也在进入复验前被排除。

**实际触发**：五份真实监控的上游节点多次成功，整轮均在 resolve_generation 失败，下一轮的应用节点命中仍为 0。当前失败轮次没有可供新轮使用的成功父 Run，属于明确的缓存准入设计问题。

**修复设计**：将纯计算阶段的已校验产物与整轮工作流交付状态分离。复用前仍匹配租户、文档/资产内容身份、节点契约、完整输入与模型/校验器语义版本，并重新完整验收；副作用节点与最终交付不得按此规则直接重放。不要仅删除状态过滤就开放所有历史节点；先建立可复用产物类型和是否纯计算的声明，并保留来源关系、原始候选及验收证据。

## C4 · P1 · 结果语义身份使用全局源码指纹，无关改动也会全量击穿缓存

**证据**：`semantic_identity.py:180-184` 每个节点缓存哈希包含 `runtime_registry_signature()`；`registry.py:268-290` 将 `modules/agent_platform`、`core/ai`、`modules/knowledge_base_components` 三个目录全部 Python 文件及处理器源码纳入摘要，`294-314` 又纳入全部内置 Agent/Tool/Workflow 和注册策略。它不按当前节点的实际依赖裁剪。

**触发**：修改一个与 source_text 无关的评测反馈模块、知识库模块或恢复器，同样改变 source_text、vision 的语义哈希。当前边修代码边重建 Run 的工作方式会持续使历史上游结果变冷；冻结旧 Run 的恢复契约也与这份全局摘要耦合。

**修复设计**：区分不可变 Run 执行版本和可复用产物的语义版本。Run 仍冻结已发布代码构建；产物身份按节点 prompt/schema/实际模型路由、直接工具以及显式声明的传递 parser/validator/normalizer 依赖清单构建。不可简单移除源码身份或绕过旧 Run 检查，也不能只哈希公开函数名而漏掉私有依赖。使用真实历史输入做相关/无关改动的失效矩阵：相关改动必须失效，无关改动应保留。

## C5 · P1 · 每轮改写 system 与首条输入，主动损害公共前缀稳定性

**证据**：`sdk_adapter.py:1633-1639` 每轮把不断变化的完整预算 JSON 拼到 system instructions；`1914-1926` 用新的完整状态观察替换历史首条 user 输入；`1780-1792` 根据当前行动目录变化 tools；`1935-1966` 还改写历史工具输出。保证状态新鲜的意图合理，但请求不是稳定前缀加末尾增量。

**结论边界**：早期字节/token 改动会让公共前缀提前分叉，后续相同证据不能作为同一个连续前缀复用。这是可确认的构造问题；不能仅凭代码认定厂商所有请求实际命中都是 0。厂商仍可能复用分叉前的稳定指令片段。

**修复设计**：固定 system 的业务/协议指令，把会变的预算和当前状态放在末尾的短消息；不可变文档证据按内容身份稳定排序并位于可变状态之前。保留原始审计历史，模型视图以版本化的短增量替代每次重写首条全量状态；应在安全控制和缓存之间设计稳定工具协议，工具权限仍由运行时校验。离线生成两轮真实请求的规范视图，记录最长公共前缀与差异位置，先证明结构改进，再在批准的小预算内检查真实命中。不能承诺必命中，亦不能为缓存而保留过期事实。

## C6 · P0 · 缓存与计费证据随运行历史一起物理删除

**证据**：`core/settings/config.py:122-123` 默认 `AGENT_RUN_HISTORY_LIMIT=1`。`run_repository.py:290-357` 删除旧终态的 approvals/events/node_runs/runs；`retention.py:20-34` 仅防止失败轮淘汰成功结果，无法保留所有失败费用证据。请求总用量、专业回执、节点缓存原始候选都存放在被删除的 Run 或 Node JSON 中。

**实际证据**：当前审计依赖手工保存的 Run45/46 snapshot 和 monitor 才能复算旧轮；新终态触发历史清理后数据库不再保留 Run43–46。若没有这些手工文件，就无法查旧失败的成本、原因和已完成结果。

**修复设计**：UI 列表保留条数与审计保留期限分开；请求费用账本、不可变产物、错误证据采用独立持久实体和引用关系，应用缓存按其有效期/容量独立回收。历史归档可以减少大 JSON，但不应删除账单事实。禁止为了节省存储清除未知用量或尚未核账的失败请求。

## C7 · P1 · 协调成本已经高于实际生成，当前不是缺一个重试开关

Run45 的 `sdk_state.error_diagnostic.model_requests` 保存了完整 160 次协调阶段诊断，可逐项重算：

| 角色 | 请求数 | 输入 tokens | 输出 tokens |
|---|---:|---:|---:|
| test_generation_coordinator | 35 | 567,614 | 10,529 |
| test_planning_scope_router | 39 | 272,047 | 118,958 |
| test_planning_route_gap_reviewer | 67 | 350,292 | 102,588 |
| test_authority_reconciliation_reviewer | 11 | 69,763 | 60,970 |
| test_business_planner | 4 | 66,119 | 29,028 |
| test_business_plan_batcher | 4 | 19,243 | 14,046 |

该阶段最后一个父协调请求输入 31,558 tokens（SDK 上下文 143,865 bytes），只输出 199 tokens；当时 generation_records 仍为 0。当前状态过滤器虽压缩部分工具输出，仍没有阻止大量重路由、复审和历史膨胀。

**修复设计**：已知状态转换、待办索引、缓存命中、批次分发、当前合法动作、完整性检查由确定性的领域状态机处理；模型只做需要语义判断的规划、冲突判断、生成和审查。为每一不可变输入版本建立唯一产物/审查身份；只重新处理受变更影响的边，禁止为相同证据和同一判断反复发完整模型请求。成本验收除 50 条最终用例落库外，还必须检查每阶段请求数、输入 token、重复身份与有用产物增量。此改造需由完整编排审计确定边界，不能靠继续提高 160 请求上限解决。

## C8 · P1 · 配置验证和保存会反复付费探测，且不进入 Agent 账本

**证据**：`core/ai/reasoning.py:48-63` 明确声明每次操作直接询问且不跨操作缓存，在五个 effort 上循环真实 POST；`98-111` 对最终选择再发一个 `hi` 请求。`routers/system/config_routes_runtime.py:167,195-211` 的去重字典只活在单次 `_validate_model_config` 调用；`219-220` 对 vision 再独立验证。`157` 的验证连接和 `244` 的保存均调用该方法，所以先验证再保存会重复探测同一配置。上述请求直接使用 httpx/provider，不经过 `AutonomousBudgetHooks` 的 Agent 账本。

**边界**：代码可以确认额外请求路径及不跨操作复用，不能据此断定这就是本次余额耗尽的主因。五份 Run 汇总也不包含这些探测费用。`probe_reasoning` 的 HTTP 2xx 只能证明服务端接受该请求，不能证明参数真的被采用，更不能证明 UI 的五档有五种独立推理行为。

**修复设计**：将配置验证也接入统一请求账本和用户预算。优先依据供应商明确能力契约/元数据，将“请求接受”“行为能力”“实际可选强度”分开。必要的真实探测需要显式计数；以规范 provider/endpoint/model/protocol/config 指纹与证据有效期复用已验证结论，保存未变化配置不重新探测；手动刷新与凭据/模型变化才重新验证。能力别名应在 UI 展示实际有效档位，不能把兼容参数被接受当成独立强度。不要为避免探测而移除配置与实际协议的一致性校验。

## 建议落地顺序

1. 维持停止实跑；先保留当前失败与用量证据。建立请求账本和跨轮硬预算，统一缓存/推理 usage，确保未知不当零。
2. 解耦纯阶段产物缓存与整轮成功状态，解耦缓存语义身份与全局构建身份；保留完整验收和租户隔离。
3. 改造稳定请求前缀、依赖失效与确定性调度；用现存真实快照离线演练命中、失效、拒绝和恢复。
4. 由用户确定明确小额费用上限后，才可进行一次有阶段止损条件的真实验收；本审计不发起该步骤。
