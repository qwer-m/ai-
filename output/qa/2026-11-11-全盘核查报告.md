# 测试开发平台：API 消耗与生成失败的全链路核查

日期：2026-11-11。对象：当前工作区代码、真实 MySQL 表结构和保留记录、Run 43–47 的真实监控、Run 45–47 的节点快照，以及已安装 SDK 和供应商官方协议。

本轮仅做只读审计与证据归档，没有调用业务模型、查询账户余额、创建任务、重跑任务、修改生产代码或迁移数据库。执行器 active/reserved 均为空；CRM Run 47 已因 HTTP 402 失败。其他项目的 Run 27 仍在等待用户确认，没有替用户操作该任务。

## 结论

问题不是 DS 没接通，也不能靠统一关闭思考或继续增加重试解决。当前设计把大量费用消耗在生成前的协调和重复验证中，又同时存在结果复用边界过严、上下文前部反复变化、费用明细丢失和跨轮没有累计止损的问题。前面的连续全量实跑在没有交付进展时仍继续消费，是本次执行判断的失误，不能归咎于用户配置或余额不足。

现有工作区的局部修补尚未证明完整交付：206 项回归检查和真实续租阻塞验证，不等于这份 CRM 文档已生成并保存 50 条用例。这次新增交付仍为 0；历史 Run 13、15 的成功属于其他旧运行，不能用来替代本次验收。

## 三、遗漏或不完整的设计

1. **工作项完成有两套口径。** Run 46 已保存 5 个通过完整校验的权威子结果，领域却仍为 0/6，因代码等整组完成才提交。它们没有全部丢失，但 UI、恢复和领域聚合必须跨两套记录解释进度。独立工作项应独立验收和提交，父聚合负责整组不变量。
2. **来源审查存在关键词门控。** `test_generation_semantics.py:2817` 对无图片、无表格且均标 effective 的纯文本，可能因没命中有限词表而跳过跨事实治理。这是覆盖缺口，未证实是此次 CRM 的直接失败原因；应通过来源条件和关系覆盖识别待审范围，不能继续加文档专用关键词。
3. **人工澄清身份不稳定。** `conflict_confirmation.py:37` 把自由文本 reason、coverage_fragment 放进问题 hash；模型换一种表达即可变成新问题。`:71` 只验证答案数量、非空和长度，不能保证答案语义完整。应将问题身份绑定来源版本、稳定覆盖目标、事实和冲突维度；答案保存可追踪条件与适用范围，仅补问真正未决部分。
4. **展示次数污染执行尝试身份。** `service.py:792` 的重置修改 run_attempt，`:677`、`:703` 又拿它决定下一次尝试编号，`_initial_run_context:97` 据此构造 attempt_id。已有多次重试后重置，再重试可复用先前编号；当前没有以 DB 唯一键保证逻辑任务内 attempt_id 不重复。显示计数应单独保存，真实 attempt 单调递增且不可改写。这是静态路径推导，没有修改真实数据制造重复。
5. **时间契约混存。** MySQL NOW 比 UTC_TIMESTAMP 快 8 小时；Run 47 created_at 为 13:44:37、started_at 为 05:44:37。部分序列化直接给 naive 时间，部分补 Z。应按字段来源分批迁移为 UTC，不能对历史所有字段统一减 8 小时；也不能据此就认定租约比较全错。
6. **成果生命周期依附 Run。** 目前“落库”实为 `run_context.artifacts.test_generation` 的 JSON 持久化，能够保存结果；问题是成果版本和运行保留周期绑定，缺少稳定的成果版本引用。先分离不可变成果及 provenance，再按查询/人工编辑需要决定是否拆分用例字段。
7. **长期上下文隔离有缺口。** `routers/orchestration/agents.py:224` 校验 project_id 所有权，却原样接受 scope_id；普通 memory 写入没有强制 user/project scope 与当前 owner 一致，检索 `context_memory_repository.py:94` 主要按 scope_id 匹配，global 也未限制平台发布权限。存在跨域知识污染风险，本轮没有插入数据，也没有现成多用户泄漏证据。写入应从可信身份推导 scope，检索同时校验 owner/tenant。
8. **动态工具审批尚未完整实现。** `sdk_adapter.py:869` 将 FunctionTool 设置为 needs_approval=False，`:2388` 明确 SDK 审批中断尚未映射；固定 tool 节点有审批，不代表 Agent 内动态工具支持 requires_approval。当前生成内置工具都是 false，因此不是此次费用故障来源。发布可配置高风险工具前应在原工具执行边界完成审批映射或显式拒绝绑定此类工具，不能静默忽略配置。
9. **连接测试覆盖不足且档位语义不准。** hi 请求被服务端接受不代表真实工具提交、结构化输出、思考历史回传组合可用。DS 当前将 medium/xhigh 映射为 high；UI 的“中/超高”不能理解为已验证的独立强度。参考[官方请求参数](https://api-docs.deepseek.com/api/create-chat-completion/)。应区分鉴权、协议、工具、视觉和能力别名的证据，避免一个“连接成功”掩盖运行时 400。
10. **观测与验证标准不完整。** 前台以阶段状态、请求次数和重置次数为主，缺少已消费/预留费用、缓存缺失原因和有效产物增量。此前测试通过后仍持续 0 交付，说明单元/协议验证不能替代端到端交付指标；真实验收必须同时读回成果、绑定和独立终审，且报告每阶段成本。

## 四、数据库应怎样改，而非全量推倒

保留 Run 的状态机、行锁、claim token、迟到提交 fencing；保留 Node 的 `(run_id,node_key,attempt)` 与事件 `(run_id,sequence)` 唯一约束、外键、来源冻结和终审门禁。JSON 不是原罪，现有全量输出复验也不应删除。

最小目标模型：

| 实体/边界 | 唯一职责 | 应移出的内容 |
| --- | --- | --- |
| 逻辑任务/预算聚合 | 任务身份、跨尝试累计上限、授权预算 | 不重置费用，不依赖可删除 Run 存历史流水 |
| Run/Node 与轻量 checkpoint | 执行尝试、所有权、当前游标、版本引用 | 逐请求费用、全部历史响应、所有产物大副本 |
| 逐请求账本 | 请求/预留/响应/中断状态、真实 usage、价格与供应商关联 | 不夹带完整领域正文；未知和已结算分开 |
| 不可变产物/验收记录 | 来源治理、解析、规划、生成、审查成果及依赖 | 不由 UI 历史清理连带删除；不永久双写多套权威副本 |
| 调度 outbox | 与业务事务绑定的待投递事件与确认 | 不另造一套 Worker 所有权 |

代码依赖稳定后再用真实 EXPLAIN 选择组合索引；当前少量 Run 下，索引不是烧费主因。不要通过增大 sort buffer 掩盖大 JSON 整行排序，也不要给每个 JSON 路径都建索引。

## 五、修复顺序与零付费验收

**第一阶段：止损、核账、保全。** 停止自动重跑；分离审计保留与 UI 列表；先实现可核对的单请求流水与任务/用户累计上限，覆盖配置验证和失败请求；402 分类清楚，禁止自动换路由继续花费。历史缺失项保持 unknown，本轮不会用新模型请求补造旧证据。

**第二阶段：重构复用与依赖。** 以已有来源/节点/验收机制为基础，先形成独立来源治理产物；解耦 Run 构建与产物语义版本；稳定事实/意图身份；缩小失效范围；改固定分片为按实际依赖与容量分片。替换后删除旧的重复缓存/状态副本，避免长期双写与兼容分支累积。

**第三阶段：收敛执行与持久化。** 确定性工作项调度，语义判断由模型承担；统一子结果与领域完成状态；稳定请求前缀；缩小事务；补投递 outbox、时间和权限约束；完善 UI 消费与有效进展展示。

先用已经保存的真实输入、真实响应和失败记录验证以下不变量，不需要新付费模型输出：

- 相同来源与语义版本已验收的纯产物可跨失败 Run 复用；来源、租户、规则或校验依赖变化时必须拒绝过期结果。
- 改无关模块不会击穿来源解析缓存；修改实际 parser/validator 则必须失效。
- 局部变更影响范围可列举；没有输入/证据/候选变化时不重复付费。
- 缓存/推理用量缺失记 unknown；同一请求不重复结算；恢复、重试、展示计数重置不刷新累计支出上限。
- 未成功的前置工作不能花掉全部交付预留；无进展时带明确证据停止。
- 已验收子工作项与父聚合一致；取消和断租不允许旧执行器提交；未知用量保留待核账。
- 提交后、投递前中断可恢复；重复投递不重复执行；审批等待期间没有付费请求。
- 运行清理后费用、失败原因和成果版本仍可读；时间、租户与来源关系不变。

本次没有实施上述重构，也没有宣称 50 条验收已通过。后续如进行真实模型验收，应另有明确小额累计预算和阶段停止条件；本轮不会再次发起。
