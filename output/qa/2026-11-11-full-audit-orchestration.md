## 仍存在的主要设计问题

### O1 / P1：先围绕未经最终治理的事实付费规划，再进行来源权威判断

**代码证据：** `backend/modules/agent_platform/test_generation_agent.py:269-296` 将草案、整合、路由、支持复核列为接受规划之前的工作；`:574-590` 在 `accept_generation_plan` 之后才准备来源权威审查；`:525-540` 在权威审查结束后重新更新支持复核输入，并撤销 accepted_plan / generation / review。

**触发与后果：** 同一来源包含原型截图、旧规则、变更说明、待定语句时，前面支持复核可能批准后来被权威专家降级的事实。系统先付费完成草案、路由和支持判断，再发现前提不可用，必须回到上游重做。Run 45 完成过 10 个权威子会话，却继续修订草案并重新运行路由，最终在生成前用尽 160 次额度。当前新增的同源 `source_authority` 保留机制修复了“结论遗失”，没有消除这个处理顺序本身。

**修复设计：** 将来源事实及其条件、实例/规范边界、冲突/替代关系先形成独立、可复用的证据治理产物。治理范围由事实及来源关系确定，不依赖之后由模型任意划分的测试模块。之后草案、规划与支持验证仅依赖已经治理的源事实版本。下游提出新的实际证据时，仅打开对应来源关系的增量治理。删除“按新测试模块重新建立来源权威范围”的旧入口，保留同一权威结果的唯一所有者。

### O2 / P1：全局规划目录进入每个路由任务，局部修订触发近全量重算

**代码证据：** `test_generation_planning.py:757-775` 给每个 scope 输入附带全部模块及其全部覆盖意图；`:801-805` 合批仍带整个 module_catalog。`test_generation_planning_agent.py:314-347` 草案变化清空整个 plan/route/gap，再用完整 JSON hash 复用旧记录；`:727-732` 一个草案不同即 `_clear_plan`。`test_generation_agent.py:442-461` 任一 source/draft/plan/support 版本变化都失效整个下游领域。

**真实表现：** Run 45 进行了 3 轮完整 scope 路由，已验收路由调用 36 次；Run 46 为 2 轮、24 次。现有结果缓存不是没有实现，而是全局目录和位置索引变化使大量原输入身份不再相同。严格 hash 拒绝复用过期结论是正确的；错误在依赖边界太大，不能靠放宽 hash 来修。

**修复设计：** 模块、意图、事实、支持边使用稳定语义 ID，避免数组序号成为身份。记录每个派生物实际读取的来源和模块目录版本，局部变更先明确影响集合；新增或修改模块时只重审相关候选及受排他归属影响的邻域。确实依赖完整目录的全局归属审查仍全局失效；不能为了缓存把真实全局依赖伪装成本地。删去同时维护 previous_plan、全局 route_cache、位置索引映射的重复身份源，统一成版本化依赖图。

### O3 / P1：支持复核按固定 3 个意图切片，却反复发送整个模块事实和原文

**代码证据：** `test_generation_planning_agent.py:908-932` 先给模块附上其全部 candidate_facts 和 scope_evidence，再仅切 `missing_test_design_items` 为每组 3 条；`:936-949` 对全部切片调用模型后汇总。`:39` 是固定常量 3。`test_generation_planning.py:1335-1355` 甚至将模块相关 scope 内全部事实作为候选，以便检测路由漏项。

**真实表现：** Run 46 当前 6 个模块分别带 58/65/54/31/23/22 条候选事实，分别有 13/15/19/10/12/9 个待审意图；按当前固定切片仅这一轮就需要 5+5+7+4+4+3=28 次支持调用，每个调用重复模块事实与原文。已验收支持调用累计 53 次。该切片修补了输出上限问题，但用输入重复和调用次数偿还输出风险，没有成本模型。

**修复设计：** 不对特定文档特调。按实际输入 tokens、预期决策输出和供应商上下文限制构造批次；先确定意图对事实/原文的依赖闭包，再发送闭包。另设一次明确的模块漏路由核查，不要要求每个 3 意图切片都重做完整候选搜索。跨条件与跨页关系必须随闭包保留；不能机械裁剪原文来制造便宜但错误的结论。

### O4 / P1：整个前置编排可吃完共享额度，没有留出生成和验收的交付预算

**代码证据：** `test_generation_builtin_specs.py:683-689` 父协调器 160 轮、6 并发；`sdk_adapter.py:2049-2056,2089-2096` 每个托管专家最多 6 轮且整体会话时间乘轮数。当前共享预算控制了硬上限，但不会在初始规划、支持复核和重规划准入前，为待生成批次、独立初审、全局审查、持久化预留最小可交付额度。父 Agent 指令 `test_generation_builtin_specs.py:678` 只要求“避免重复”，并非可执行的准入约束。

**真实表现：** Run 45 的 160 次全部花在生成之前；Run 46 111 次仍未进入用例生成。Run 47 仅 50 条目标的上游 source_text/source_vision/plan_batches 就已用 21 次成功响应，输出 66,711 tokens，随后规划整合一次会话又调用 3 次。不能用“160 次没超限”解释为预算设计正确。

**修复设计：** 从真实任务图估计前置成本和剩余最小交付成本，在每个昂贵子图准入前统一检查请求、tokens、费用及时间预算。规划修复只能消费单独有限的返工份额；不足时输出可解释的暂停/失败和已保存产物，不继续抽取直到账户 402。额度数值应来自明确用户预算和供应商用量，不通过增加 160 或关闭思考掩盖问题。费用计量和厂商缓存命中审计由独立成本核查报告展开。

### O5 / P2：模型被反复用于协议纠错和确定性前置步骤，缺少无进展收敛条件

**代码证据：** `sdk_adapter.py:1720-1745` 模型返回普通正文时追加提示继续，直到剩余轮数耗尽；`autonomous_tools.py:95-128,184-212` 将 Schema/领域准入错误反馈回模型；`:77-83` 限制累计工具数量，没有针对连续无进展的状态/失败类别上限。`test_generation_agent.py:251-319` 已能用代码推导合法步骤，但除最终 finish 外仍让模型选择大量确定性前置动作。

**真实表现：** Run 45 有 16 次失败动作，包括在不可用状态调用生成/审查、空 changes、缺 problem_ids、重复请求不需要的重建。Run 46 有 6 次失败动作。Run 47 真实业务规划专家第一响应恰好消耗 12,000 输出 token，上下文随后从 1 条输入增长到 4、7 条，三次调用合计实际输入 50,044、输出 16,178 tokens 才完成规划提交。该记录证明协议/校验纠错可以是大头，不能只统计成功业务动作数。

**修复设计：** 把确定性 prerequisites、当前全部待办派发、接收/聚合和终止放回显式编排器；模型仅承担需要语义判断的业务规划、争议裁决和真实修复分支。连续相同领域版本无进展、同类协议失败或输出截断应达到明确预算后停止并呈现诊断；不能持续添加“请继续”的提示。终止工具验收继续严格，不能将自由正文直接当成功。需要阶段有语义决策时保留模型能力，不做全链路思考模式关闭。

### O6 / P2：独立工作项的完成状态与父动作的原子状态粒度不同，故障反馈失真且恢复过重

**代码证据：** `test_generation_agent.py:645-649` 等全部 authority outputs 返回后才 `apply_authority_action`；`:625-635` 批量设置 records。支持复核同样 `test_generation_planning_agent.py:936-949` 先等待所有切片，再一次更新。SDK 已另存 validated_agent_calls，父动作异常则 `autonomous_tools.py:184-203` 恢复 previous_state 并保存失败回执。

**真实表现：** Run 46 最后快照 `authority_records` 为 0/6，但 SDK 已保存 5 条通过验收的权威子会话。恢复可以复用这些回执，因此不能声称这 5 批“全部丢失”或都重新计费；但领域进度看上去为零，且一次长尾会将整个动作停留 started，必须跨父级动作恢复才能转成领域状态。UI 和预算账本必须读取另一个存储事实才能解释真实进度。

**修复设计：** 为每个稳定工作项持久化输入版本、请求尝试、结果验收及费用；独立项验收通过即提交其状态，父聚合仅在当前完整依赖集合齐备后生成统一产物。取消或失败不能使已独立验收的 work item 回滚成未开始；整组不变量仍由聚合器校验。消除 SDK 子回执缓存与领域 records 两套“完成”口径，避免 UI 只展示其中一个。

### O7 / P2：权威审查的准入以有限词表和媒体类型替代完整的来源关系覆盖

**代码证据：** `test_generation_semantics.py:44-56` 定义“替代、作废、废弃、修订、不再、取消、暂不、非最终、以配置为准、以后台为准、以运行时为准”的有限词表；`:2817-2834` 只有表格、图片、非 effective、既有 governed_by 或命中该词表才激活权威复核；`:2919-2927` 否则整模块跳过。

**确定的覆盖缺口：** 跨段或跨页的纯文本事实，即使在相同条件下给出相反操作，只要提取器各自标为 effective、没有结构化治理边且用词未命中上述词表，就不会进入跨事实权威审查。这里确认的是当前分支的覆盖不足，未声称本次 CRM 失败已由这一分支触发；CRM 许多模块因图片而被激活了。

**修复设计：** 来源提取阶段显式产出条件、主体、行为、结果与可追踪原文关系；合并阶段按真实关系检测待核对冲突、版本或配置边界。关键词只能成为可解释的候选信号，不能成为“无需审查”的唯一证明。结合 O1，将该责任归于独立来源治理产物，删除后置按模块/媒体激活整块大审查的旧门控。

## 已修补但还不能当成端到端验收通过的历史故障

- DeepSeek 思考与强制工具协议：当前已转换成 auto 并保持最终提交校验；不能再把普通模型输出当成功。副作用是更多协议往返，见 O5。
- 连接故障使独立兄弟任务被取消：当前 `registry.py:66-78,112-124` 已对明确的暂态传输异常等待独立兄弟收敛并保存回执。非传输性致命错误仍会按 TaskGroup 取消兄弟，这是当前错误隔离边界；不能宣称任何失败都已独立隔离。
- 90 秒 HTTP 超时被用作完整多轮会话超时：当前拆为单次 HTTP 和子会话总时长，但把总时长乘 6 只是上界，不是每阶段完成性/成本设计。
- 同源权威结论在草案或计划变化后丢失：当前新增 `source_authority` 和同源保留，真实回放已检查影响范围；本轮真实运行未到达完整生成，不能宣称生产闭环已验证。
- 租约续期绑定事件循环：当前改为独立续租线程，真实数据库 30 秒租约、40 秒阻塞验证通过；恢复还新增结束失权旧节点尝试。Run 47 在规划时因 402 结束，尚未证明长权威审查阶段全链路正常。

## 应先完成的设计收敛

1. 先停止真实付费重跑，保留失败快照、逐次模型用量与当前代码版本；账单/厂商命中率不能用推测补齐。
2. 先建立“来源治理产物→稳定事实/意图 ID→增量依赖→工作项请求→验收产物”的单一数据流，再删除以全局状态反复重建目录、全量路由和重复完成口径的旧链路。
3. 先用已保存真实输入、输出、失败回执验证依赖失效、最小交付预算及停止条件；无需再购买模型输出证明调度器和账本正确。
4. 新设计验收至少包含：局部来源修订的影响集合、无变化输入零请求、失败重试仅重跑未完成工作项、断租旧提交被拒绝、HTTP 402 明确识别并停止、达到预算前保留可解释交付状态。真实模型小额验收应由用户另行同意预算后执行。

本报告未将所有文件的存在、参数大小或架构复杂本身当缺陷；结论均指向实际依赖关系和已有运行证据。其他模块、数据库表设计和厂商缓存统计由另外的专项审计覆盖。
