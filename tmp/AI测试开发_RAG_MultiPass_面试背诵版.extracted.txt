AI测试开发（RAG + Multi-pass）面试背诵版
按“面试官提问 -> 标准回答 -> 追问展开 -> 常见误区纠正”整理
使用方式：先背“一句话标准回答”，再看“展开版”和“误区纠正”。这份文档重点不是术语定义，而是把你这个窗口里已经聊过的核心问题，整理成能直接复述的面试答案。
一、RAG 基础三段：Recall / Rerank / Compression
面试官问：先讲一下 Recall、Rerank、Compression 分别是什么。
标准回答：Recall 是第一阶段，从知识库中召回候选 chunk，目标是高覆盖，尽量别漏；Rerank 是第二阶段，对候选结果做更精细的排序和筛选，目标是高精度，尽量选准；Compression 是在 token 限制下压缩和裁剪上下文，提升信息密度，让最终喂给模型的内容更有效。
展开回答：这三段本质上是一个漏斗。Recall 负责“找全”，Rerank 负责“选准”，Compression 负责“喂好”。Recall 可以带一点噪声，因为后面还有 Rerank；但如果 Recall 阶段漏掉关键内容，后面任何阶段都补不回来。Compression 通常放在 Rerank 之后，因为先排序、再压缩，精度更稳。
常见误区：Recall 不是“再次召回”，它本身就是第一次从知识库取候选；Rerank 也不等于简单重排无序 chunk，它是在候选池上做精细筛选。
面试官问：为什么 Recall 要放宽一点？
标准回答：因为漏召回是不可恢复的，而噪声是可以通过 Rerank 过滤的。
展开回答：如果 Recall 太严格，候选池里根本没有正确 chunk，Rerank 再强也无能为力；如果 Recall 稍微宽一点，候选池里多带一些噪声，后面仍然可以通过打分和排序把最相关的内容挑出来。所以工程上通常是 Recall 放宽，Rerank 精筛。
常见误区：不要把“放宽 Recall”理解成无脑多拿。放宽是为了提高覆盖，不是为了让候选池无限膨胀。
面试官问：Compression 会不会损失信息？
标准回答：会，这是不可避免的 trade-off，但目标不是零损失，而是在有限 token 预算下优先保留对当前 query 最有价值的信息。
展开回答：工程上不会随机裁剪，而是先经过 Rerank，优先保留高相关 chunk；同时保留关键结构信息，例如标题、命中 query 的段落、关键字段。还可以记录压缩前后 token 数、保留 chunk 数和来源分布，让压缩是否过度变得可观测。
常见误区：Compression 不是简单截断，更不是“压得越狠越好”。压缩过猛会损伤生成质量。
二、Recall 细化：original / rewrite / raw / summary / lane / quota
面试官问：你们说的 original query、rewrite query、raw index、summary index 分别是什么？
标准回答：original query 是用户原始问题，rewrite query 是对原问题做改写后的检索问题；raw index 是原始文档 chunk 的索引，summary index 是摘要化后的 chunk 索引。
展开回答：original 更精确，rewrite 覆盖更广；raw 信息更完整，但噪声更大；summary 信息密度更高，但可能丢细节。把这些组合起来，可以形成多条检索路径，彼此补足。
常见误区：不要把 rewrite 理解成 rerank，也不要把 summary 理解成最终答案，它只是文档侧的一种检索形态。
面试官问：什么是 multi-lane recall？lane 是什么？
标准回答：lane 可以理解为一条独立的召回路径，本质上是“查询方式 × 索引形态”的组合。multi-lane recall 就是并行使用多条不同的召回路径来提升覆盖率和鲁棒性。
展开回答：例如可以有四条 lane：original + raw，original + summary，rewrite + raw，rewrite + summary。每条 lane 都有自己的特点，合起来比单一路径更稳。
常见误区：lane 不只是“道路”这个字面意思，面试里更准确的说法是“独立召回策略单元”。
面试官问：quota 是什么，为什么需要 quota？
标准回答：quota 是每条 lane 允许返回的候选数量配额，用来控制不同召回路径的贡献比例。
展开回答：如果没有 quota，某一类信号可能会垄断结果，例如 embedding lane 过强，导致 keyword 或 summary lane 的结果挤不进候选池。设定 quota 以后，系统能保留更多样的候选来源，提高稳定性和多样性。若某个 lane 命中不足，还可以把剩余 quota 回收给其他 lane。
常见误区：quota 不是死规则，它是工程调优手段，可以结合命中率、AB test、rerank 后表现持续调整。
三、Rerank：base score / bonus / final score
面试官问：你们的 rerank 是怎么打分的？
标准回答：我们通常会把 rerank 拆成 base score、bonus 和 final score。base score 反映通用相关性，bonus 反映业务规则加权，final score 是最终排序依据。
展开回答：base score 可以融合 embedding similarity、keyword match、title match 等信号；bonus 可以来自业务先验，比如标题命中加分、高质量文档加分、关键字段命中加分；最终通过加权融合得到 final score。这样做兼顾了泛化能力、可控性和可解释性。
常见误区：不要把“快乐打分”说得太口语。面试里更标准的叫法是“多信号融合的基础相关性评分 + 业务规则加权”。
面试官问：为什么不用一个模型直接做 rerank，而要加这么多规则？
标准回答：主要是成本、可控性和可解释性三方面原因。模型直接对大候选池做 rerank 成本高，且业务场景下某些规则信号模型不一定稳定学到，因此需要规则辅助。
展开回答：如果候选很多，直接上重模型 rerank 会拉高 latency 和成本；而且纯模型方法虽然强，但不够透明，业务方很难知道为什么某个 chunk 排前面。规则并不是替代模型，而是把业务先验显式注入，例如标题命中、接口名、字段名、规则 id、文档质量等。这能显著提升稳定性。
常见误区：不要把答案说成“模型一口吃不下”就结束。更完整的答案必须包含成本、可控性、可解释性。
面试官问：top_k 应该放在 recall 还是 rerank？
标准回答：两层都有 top_k，但含义不同。Recall 阶段控制候选池大小，通常较大；Rerank 阶段控制最终输出大小，通常较小。
展开回答：Recall 的 top_k 决定后续可供精筛的搜索空间，通常要放宽；Rerank 的 top_k 决定最终进入 compression 或 LLM 的高质量结果，通常更严格。所以不是“只放一个 top_k”，而是前大后小。
常见误区：只回答“放在 rerank”不够完整，因为 Recall 如果没有自己的候选池上限，系统成本会失控。
四、Recall@k / Precision@k / trade-off / latency
面试官问：precision@k 和 recall@k 分别是什么意思？
标准回答：precision@k 指前 k 个结果中相关结果所占比例；recall@k 指前 k 个结果中覆盖到了多少相关结果。
展开回答：在 RAG 中，Recall 更关注 recall@k，因为它的目标是别漏；Rerank 更关注 precision@k，因为它要保证前面送给模型的结果尽量准。
常见误区：不要把 precision@k 翻成“快乐打分”，它更准确的中文是“前 K 个结果的准确率”或“前 K 个结果中的命中率”。
面试官问：recall@k 和 precision@k 在实际系统里怎么 trade-off？
标准回答：核心是在覆盖率和精度之间做权衡。Recall 候选池越大，覆盖越高，但噪声也越多；候选池太小，precision 可能表面上高，但会漏掉关键信息。
展开回答：对于 multi-lane + rerank 结构，通常做法是先让 multi-lane recall 尽量把可能相关的内容找全，再由 rerank 把 precision 拉上来。工程上通过调 recall top_k、lane quota、rerank cutoff 等参数来平衡二者。
常见误区：不要以为 precision 高就一定好。如果正确答案根本没被召回，precision 再高也没意义。
面试官问：latency 和 trade-off 中文怎么说？
标准回答：latency 是延迟或响应时间；trade-off 是权衡、取舍。
展开回答：在系统设计题里经常会说“在质量和 latency 之间做 trade-off”，意思就是：更多 pass、更多规则、更多模型会提高效果，但会拉高响应时间和成本，需要平衡。
常见误区：trade-off 不是“关闭某个东西”，而是两类目标之间的平衡。
五、Context Compression：token budget / fallback / 观测
面试官问：token budget 是什么？
标准回答：token budget 是给模型输入上下文预留的 token 上限。
展开回答：它不是单个 chunk 的最大值，而是“prompt + system 指令 + 上下文 chunk + 输出预留”共同受模型上下文窗口限制。工程上通常会给 context 留一个预算区间，例如总窗口 16k 时，给上下文留 6k 到 10k 左右，其余给 system prompt、用户问题和输出。
常见误区：不要把 token budget 理解成“单个 chunk 最大长度”，它是整体预算。
面试官问：压缩后上下文质量足不足，你怎么知道？可以观测吗？
标准回答：可以观测。一般会结合相关性分布、保留 chunk 数量、来源多样性和最终生成效果来判断。
展开回答：例如压缩后如果平均 rerank score 很低、保留 chunk 数过少、来源过于单一，或者最终生成的质量明显下降，就说明压缩过度。还可以记录压缩前后 token 数、chunk 数、文档来源分布，这些都属于 compression stats。
常见误区：不要把“质量足不足”理解成完全靠主观感觉。工程上可以通过日志和指标显式观测。
面试官问：fallback 是什么意思？是不是回归？
标准回答：不是回归。fallback 更准确的中文是兜底策略或降级策略，表示当当前方案效果不好时，退回到更稳的策略。
展开回答：例如压缩后上下文质量不足，就可以放宽 token budget、增加候选 chunk 数、减少 summary 压缩强度，甚至重新 recall 一轮。它的作用是防止系统在极端情况下因为压缩过猛而丢掉关键上下文。
常见误区：fallback 不是 regression test，二者完全不同。
面试官问：Compression 应该发生在 rerank 之前还是之后？为什么？
标准回答：通常放在 rerank 之后。因为 rerank 需要更完整的候选信息来做准确排序，而 compression 会裁掉信息，如果放前面容易影响排序精度。
展开回答：更合理的顺序是 Recall -> Rerank -> Compression -> LLM。先把候选找全并精筛，再在有限预算下压缩成最有价值的上下文。
常见误区：不要把 compression 和 rerank 混成一个步骤。两者目的不同：一个是排序，一个是控制上下文密度。
六、Multi-pass / closed-loop / early-stop
面试官问：什么是 multi-pass？
标准回答：multi-pass 是把一次性生成拆成多轮，通过生成、评估和反馈不断逼近更优结果的策略。
展开回答：single-pass 是“一次出结果”，multi-pass 是“逐步优化”。它能提升覆盖率、控制质量、提高稳定性，尤其适合复杂测试用例生成、RAG 增强生成和质量闭环场景。
常见误区：不要把 multi-pass 简单理解成“多跑几次模型”。关键是每一轮之间有明确的反馈和优化目标。
面试官问：什么是 closed-loop workflow？
标准回答：closed-loop workflow 指系统输出会反过来影响下一轮输入，从而形成反馈闭环。
展开回答：在测试用例生成场景里，可以先生成候选，然后 Judge 或规则评估结果，再根据评估发现的问题去补生成、修优先级或修结构。这样就是生成 -> 评估 -> 再生成的闭环。
常见误区：只做生成而没有反馈的，是 open-loop，不是 closed-loop。
面试官问：early-stop 是什么，多早才算早？
标准回答：early-stop 是边际收益明显下降时停止迭代的策略。所谓“早”，不是按固定轮次，而是相对于继续迭代的收益已经不值得。
展开回答：常见触发条件包括：覆盖率提升接近停滞；新增 case 大量重复、低价值；Judge 评分基本稳定；新增 case 对整体质量没有明显改善。early-stop 的本质是在质量收益、成本和 latency 之间做 trade-off。
常见误区：不要把 early-stop 理解成“越早越好”，也不是“固定第 3 轮就停”。它是基于收益判断。
面试官问：你怎么判断覆盖率不再提升？
标准回答：可以从规则覆盖、去重后的新增比例，以及更高级的语义覆盖指标来判断。
展开回答：如果系统有规则、需求点或场景点清单，可以直接统计覆盖率；如果没有明确规则集，可以看每一轮新增 case 去重后还剩多少，以及这些新增内容是否真正覆盖了新的业务场景。更高级一点还可以做语义聚类，看新增内容是否只是重复表达。
常见误区：不要把“case 变多了”直接等同于“覆盖率提升了”。重复和同质化会制造假增益。
七、你这套系统的 pipeline 应该怎么讲
面试官问：pipeline 是什么意思？
标准回答：pipeline 是由多个处理阶段组成的数据处理链路，一个阶段的输出会成为下一个阶段的输入。
展开回答：在 RAG 和 AI 测试生成里，pipeline 强调的是分阶段的数据流，不只是泛泛而谈的“流程”。例如先检索、再排序、再评估、再修正。
常见误区：只说“pipeline 就是流程”太泛，面试里容易显得理解不深。
面试官问：你这个 multi-pass pipeline 到底应该怎么画？Judge 算哪一层？
标准回答：更合理的抽象是：Pass1 做 multi-lane recall 和候选生成，Pass2 做 rerank 或筛选，Pass3 做 Judge/质量评估，Pass4 做补全和修正，再决定是否 early-stop。Judge 更适合放在评估层，而不是简单叫“后处理”。
展开回答：如果你的系统是测试用例生成平台，可以这样讲：首先通过 multi-lane recall 准备上下文并生成候选；然后对候选做优先级、相关性和结构筛选；再通过 Judge、规则、质量评估或样本池诊断问题；最后根据评估结果补全缺口、修正优先级或重生成。这样闭环更清晰。
常见误区：不要把 Judge 简单说成“后处理逻辑”，否则面试官会问你它为什么能驱动下一轮优化。它实际上承担了评估和反馈职能。
面试官问：多路召回、多路重排、异常样本池分别在 pipeline 哪？
标准回答：多路召回属于 Pass1 的 Recall 层；重排属于 Pass2 的 Rerank 层；异常样本池通常属于 Pass3 的评估诊断层，同时也是离线优化资产。
展开回答：样本池并不一定每次都直接参与在线主链路，它更常见的作用是支撑评估、调参、提示词修正和规则修正。若你的 Judge 逻辑会结合样本池特征做判定，也可以说它在线上评估层有引用，但它的核心价值仍然偏向长期优化。
常见误区：不要把样本池说成纯在线链路的一部分。多数情况下它是“在线评估 + 离线迭代”之间的桥梁。
八、系统设计题到底让你做什么
面试官问：如果让我“设计一个 AI 测试生成平台”，这是要我现场实现吗？
标准回答：不是。系统设计题重点是架构抽象、模块划分、关键数据流、指标和 trade-off，不是现场写完整代码。
展开回答：面试官想听的是：入口数据是什么、知识库怎么组织、Recall/Rerank/Compression 如何设计、生成怎么评估、Judge 怎么闭环、样本池如何沉淀、怎么做 early-stop、怎么观测质量和 latency、如何做扩展和降级。你不需要现场写 FastAPI 和数据库表。
常见误区：不要把系统设计题理解成“让我把整个项目实现一遍”。重点是结构化表达。
面试官问：你的 pipeline 是同步还是异步？为什么这样设计？
标准回答：逻辑上它是顺序的，因为前一阶段输出要成为后一阶段输入；但执行层可以是异步或并发的，以降低 latency、提高吞吐。
展开回答：例如多 lane recall 可以并发发起，部分评估任务可以异步落地，离线样本池分析也可以异步跑。但整体逻辑顺序仍然是 Recall -> Rerank -> Judge -> Refine。也就是说，逻辑顺序和执行方式要区分开。
常见误区：不要说“因为上一阶段输出给下一阶段，所以它是异步的”，这把逻辑顺序和执行模型混淆了。顺序链路通常是逻辑同步的，但技术执行可以异步。
九、可直接背诵的总括答案
面试官问：一句话概括你这套系统。
标准回答：我们把 AI 测试生成系统设计成一个带反馈闭环的 multi-pass pipeline，通过 multi-lane recall 提高覆盖率，通过 rerank 提高精度，通过 context compression 控制 token 成本，再通过 Judge、规则和样本池驱动持续优化，并用 early-stop 在质量、成本和 latency 之间做平衡。
展开回答：如果面试官继续追问，可以按“Recall 找全、Rerank 选准、Compression 喂好、Judge 评估、Refine 补全”的顺序展开，再补充 quota、top_k、fallback、compression stats、规则覆盖和异常样本池。
常见误区：不要只背大词，不会落到自己系统上。最加分的点永远是：你能把这些抽象概念和你自己的工程实现对上。
十、最后一页：速记版
Recall 找全，Rerank 选准，Compression 喂好。
Recall 可以带噪声，但不能漏关键；漏召回不可恢复。
multi-lane = 多条召回路径；quota = 每条路径的配额。
Rerank = base score + bonus -> final score。
top_k 前大后小：Recall 控候选池，Rerank 控最终输出。
Compression 放在 Rerank 后；token budget 是整体上下文预算，不是单 chunk 限制。
fallback 是兜底策略，不是回归测试。
closed-loop = 生成 -> 评估 -> 再生成。
early-stop = 边际收益下降时停止，不是固定轮次停止。
系统设计题重点是架构、数据流、指标和 trade-off，不是现场写完整代码。
